Motivation

Why This Project Exists

TIBCO BWCE integration projects follow precise, opinionated conventions — repository naming, template selection, environment variables, CDM flags, and Bitbucket project alignment. Getting all of those right by hand is repetitive, error-prone, and takes specialist knowledge that not every developer has on day one.

The goal is not to replace existing tools — it is to wrap them with an intelligent layer that guides developers through the right choices, enforces TIBCO conventions automatically, and gives operations teams a single reliable source of truth for every generated artifact.
🗣️

Natural Language Input

Developers describe what they need in plain English. The AI extracts source system, target system, business object, interface type, and more — no YAML or JSON required to get started.

🧭

TIBCO Template Intelligence

The generator understands BWCE template types (pub, sub, service), CDM patterns, S/4HANA source adapters, AFS targets, and how they map to the correct shell script flags and directory layout.

✅

Built-In Guardrails

Field validation, email domain checks, URL format enforcement, duplicate-repository detection, and repository name length limits are all enforced before a single file is written.

📦

Idempotent Code Generation

If a repository was already generated the service returns the existing metadata immediately, preventing duplicate scaffolds and saving CI/CD pipeline time.

🗂️

Centralised Registry

Every generation is logged in an SQLite database and a CSV tracker. Operations can audit every artifact — who requested it, when, and which template was used.

🚀

Kubernetes-Ready Output

Generated repositories include CI/CD scaffolding and Kubernetes manifests aligned with the BWCE deployment model, ready for the operations team to promote through environments.

TIBCO-Specific Intelligence

Validations & Development Guardrails

Unlike generic scaffold tools, every rule below is derived directly from BWCE platform conventions and field experience.

Repository Naming Rules

Names are built as {source}-{object}-{target}-{type}, sanitised to lowercase kebab-case, and enforced against a configurable maximum length. Unsafe characters are automatically removed.

Interface Type Enforcement

Only pub, sub, and service are accepted. Natural-language aliases (e.g. "publish", "consumer", "API") are resolved to the correct canonical value.

Template Auto-Detection

The engine scans the templates/ directory and scores candidate templates against source, target and interface type, returning the closest match with a confidence log.

CDM Flag Awareness

Common Data Model integrations require specific template variants. The chatbot asks about CDM when the interface context implies it and adjusts the template selection accordingly.

Duplicate Detection

Before scaffolding, the registry is queried by repository name. Existing entries are returned immediately with a duplicate flag — no files are written twice.

Email & URL Validation

Email addresses are checked for format and against an allowlisted domain set. Bitbucket URLs are validated with a strict regex before any Git operation is attempted.

Scenario & Interface ID Cross-Check

Known IKD scenario IDs and interface IDs are loaded from configuration files and used to validate or suggest corrections, reducing runtime failures in downstream pipelines.

Country Code & Unique ID Normalisation

Null-equivalent values (NA, NONE, 1NONE) are normalised uniformly so the repository name is never polluted with placeholder tokens.

Environment & BW Profile Defaults

Environment (DEV/TEST/PROD) and BW profile default safely to DEV / default when not supplied, matching the BWCE deployment model expectations.

Agent Architecture

How the Agents Are Called

The system uses a layered, pipeline-style agent model — each layer adds intelligence without depending on the next. If an LLM is unavailable, the system falls back gracefully.

1

User Interface — Entry Point

A request originates from one of three surfaces: the Web Chat UI (/), the REST API (POST /api/chat/message), or the interactive CLI. All three funnel into the same processing pipeline.

templates/chat.html src/api.py src/interactive_chatbot.py
2

Session Manager Agent

FastAPI maintains a per-session InteractiveBWCEChat instance, keyed by session_id. This preserves conversation history, the partially-filled IntegrationSpec object, and which fields have already been asked about — enabling true multi-turn dialogue with no server-side state loss.

chat_sessions dict POST /api/chat/init POST /api/chat/reset
3

NLU / Regex Extraction Agent (always runs, no LLM required)

The first intelligence layer runs entirely in-process using compiled regular expressions. It identifies source and target systems, business objects, interface types (pub/sub/service), scenario IDs, CDM mentions, and country codes from the raw user message — with zero latency.

src/chatbot.py → parse_nlu() pattern matching alias resolution
4

LLM Semantic Extraction Agent (optional, pluggable)

When an LLM backend is configured (Ollama, OpenAI-compatible, or LM Studio), the message plus current spec context is sent as a structured prompt. The LLM returns JSON with any additional fields it inferred from context. Results are merged with the regex output — the regex takes precedence for deterministic values, the LLM fills in semantic gaps.

src/chatbot.py → LLMBackend.chat() llm_extract() merge_llm_into_spec() Ollama / OpenAI
5

Field Completeness & Question Generator Agent

After each extraction pass, IntegrationSpec.missing_required() checks which of the five required fields are still absent (source_system, target_system, business_object, interface_type, template_type). The next unanswered question is generated contextually — the agent never asks for the same field twice.

IntegrationSpec.missing_required() asked_fields tracking pending_field state
6

Template Selector Agent

Once the spec is complete, the TemplateEngine scans the templates/ directory and scores each candidate against the source/target/interface tuple. The highest-scoring template is selected and materialised into the workspace path with all variables substituted.

src/accelerator/template_engine.py TemplateEngine.materialize()
7

Validation Agent

Before any file is written, InputValidator enforces all TIBCO-specific rules: required fields, email domain allowlist, Bitbucket URL format, interface type membership, and repository name length. Any violation raises a ValidationError that is returned as a structured API error — not a silent failure.

src/accelerator/validators.py InputValidator.validate() ValidationError
8

Naming Engine Agent

NamingEngine constructs the canonical repository name following the {source}-{object}-{target}-{type} convention, appends country code and unique ID only when non-null, sanitises the result to kebab-case, and enforces the maximum length constraint.

src/accelerator/naming.py NamingEngine.build_repository_name()
9

Accelerator Service — Orchestrator

AcceleratorService.generate() orchestrates all downstream agents in sequence: normalise → validate → name → registry check → template materialise → write runtime config → create remote repository → scaffold CI/CD → initialise Git → register result → notify. A single method call triggers the full pipeline.

src/accelerator/service.py AcceleratorService.generate() POST /generate
10

Registry & Notification Agents

GenerationRegistry writes the result atomically to SQLite and the CSV tracker. NotificationSender dispatches a completion notification (e.g. email or Teams webhook) if configured. The API response includes the repository name, URL, workspace path, and full metadata.

src/accelerator/registry.py src/accelerator/notify.py GenerationResult
